# Координация субагентов

Ведущий отвечает за результат целиком. Сам выбери минимальное число субагентов и их специализации по тому, какие решения и проверки требуются. Для простой однозначной операции с прямой проверкой достаточно ведущего. Для существенного изменения с одной цепочкой работы достаточно автора и независимого критика. Добавляй исполнителя, когда у него есть отдельный проверяемый результат и среда поддерживает делегирование.

## Разделение работы

- До запуска определи цель каждой ветви, входные материалы, зависимости, область чтения или записи и ожидаемое свидетельство результата. Объедини поручения с одинаковым результатом. Назначай роль по задаче, например проследить путь данных или проверить оформление заказа на телефоне.
- Независимые ветви запускай параллельно. Получи общий контракт или ответ владельца до зависимой работы. Непонятное бизнес-правило передай ведущему для уточнения у пользователя. Пока ответ ожидается, продолжай независимые части.
- У каждого изменяемого файла один исполнитель в данный момент. Общий контракт, схему или итоговое объединение поручай одному интегратору. При неожиданном пересечении останови затронутые правки, сверь фактическое состояние и перераспредели владение. Сохраняй уже внесённые пользователем изменения.
- Передавай только необходимые безопасные материалы. Все участники соблюдают режим и границы исходного запроса, включая только чтение при аудите. Используй обезличенные примеры и снимки. Секреты, персональные данные и внутренние материалы вне разрешённого контекста исключи из поручений и отчётов.

## Независимая проверка

Для существенных архитектурных решений, изменений кода и дизайна привлеки критика, который не создавал проверяемый результат. Один независимый критик может охватить несколько затронутых областей. Дай ему режим только чтения, исходную задачу, ограничения и доступ к первичным свидетельствам. Для архитектуры это пути в текущем проекте и требования, для кода — итоговый diff и реальные проверки, для дизайна — сценарий и просмотренные снимки на целевых размерах, включая пары до и после правки.

Для критика выбери свежий контекст без истории исполнителя, если средство делегирования это поддерживает. Например, в среде с параметром `fork_turns` подходит значение `none`. Передай нужные исходные материалы явно. Если унаследованный контекст недоступен, такой запуск годится для одной повторной попытки в пределах тех же полномочий. Подтверждай независимое ревью полученным заключением.

Попроси критика самостоятельно найти расхождения и указать место, последствие и способ проверки. Ведущий сверяет выводы исполнителей и критика с фактическими файлами, снимками и результатами команд. Разногласие разрешай по свидетельству. Если для выбора нужно бизнес-решение, спроси владельца. После существенной коррекции верни затронутую часть критику и повтори соответствующую [проверку](verification.md).

Если субагенты недоступны, выполни доступную работу сам и явно укажи, что независимая проверка не состоялась. Сбой, пропуск, нерешённое замечание и предел проверенного отрази в результате и в разрешённой записи о проекте. Статус готовности определяй по объединённому результату.
